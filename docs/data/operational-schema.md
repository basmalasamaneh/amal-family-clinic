# Operational schema contract

## Boundary and installation

`lib/db/migrations/0001_operational.sql` creates **only** the `operational`
schema, its objects, and the dedicated `amal_demo_reset` NOLOGIN role. It does
not read or alter the immutable `public.clinics`, `public.doctors`,
`public.patients`, `public.appointments`, `public.patient_visit_history`, or
`public.calendar_app_export` tables, their privileges, or seed guards.
The previously installed `amal_app` role must already exist.

The administrative migration runner must execute this SQL once, in its tracked
transaction, before population. Do not use `drizzle-kit push` against the combined
source/operational model inventory: the hand-written migration also supplies
permissions, deferred constraints, and trigger invariants not represented by
Drizzle's schema generator. Population/reset commands and verified fixture
counts are documented in [operational-demo.md](operational-demo.md).
The migration has been applied and tested against the development database.

Drizzle exports retain the existing immutable, unprefixed seed models. All new
table exports use `operational` prefixes:

## Identity, provenance, and time

Five copied tables keep every original column and integer primary key:
`clinic_id`, `doctor_id`, `patient_id`, `appointment_id`, and `visit_id`.
All primary keys, including additional fixture tables' `id`, are
`GENERATED BY DEFAULT AS IDENTITY`; explicit preserved IDs and newly allocated
IDs are both supported. Population must advance each affected identity sequence
above its largest preserved/fixture ID, inside its serialized transaction.
Sequence gaps after rollbacks are normal and are not duplicate logical fixtures.

Every non-source table has nullable, unique `fixture_key text`, except
`import_rows`, whose stable identity is unique `(batch_id, source_event_id)`.
Ordinary non-fixture application inserts may leave `fixture_key` null.
Copied source tables intentionally have no fixture key; their original IDs are
stable. `appointments.source_ref` and `client_op_id` are independently nullable
and unique. Sync `client_op_id` is required, nonblank, unique text; it is not a
UUID-only field and is not globally unique across both tables.

Already-normalized source `scheduled_at` instants must be copied directly,
without a second Asia/Hebron-to-UTC conversion. All operational instants use
`timestamptz`, birth/visit/KPI dates use `date`, and clinic hours use local
`time without time zone`. The default clinic timezone is `Asia/Hebron`.
`working_days` uses JavaScript weekday numbering, Sunday **0** through Saturday
**6**, default all days `[0,1,2,3,4,5,6]` (no inferred weekend). Default hours are 08:00–17:00,
slot size 30 minutes, and network mode Full. Explicit fixture values may differ.
Working days must be nonempty, distinct, contain no nulls, and have values 0–6;
hours must open before closing (overnight hours are not represented).

## Relationships and validation

- Doctors require a unique email and home clinic; user linkage is nullable and
  unique. Users require unique email and nonblank password hash. PIN hashes are
  nullable but nonblank if present. These columns hold hashes, not plaintext;
  schema validation cannot establish whether a string was securely hashed.
  Locale defaults `ar`, theme `light`.
- Administrator users may be network-wide or clinic-associated, and cannot carry
  `doctor_id`. Receptionists require a clinic and no doctor. Doctor users require
  both clinic and doctor. Reciprocal doctor/user FKs and their final-state
  consistency checks are **DEFERRABLE INITIALLY DEFERRED**. Insert both sides and
  set `doctors.user_id` before commit. A linked user must have role doctor,
  matching `doctor_id`, and the same clinic. Drizzle references expose relations
  but cannot express this deferral; SQL is authoritative.
- Devices belong to clinics. Sync operations' composite FK enforces that their
  device belongs to their clinic. Device labels are translation keys.
- Patients preserve original name, phone, and DOB; normalized name is separate
  and required. Nonblank validation never trims or transforms source values.
  Phone remains text, preserving leading zeros. DOB cannot follow `minor_as_of`.
  `is_minor` is a stored generated boolean:
  `minor_as_of < (dob + interval '18 years')::date`.
  `minor_as_of` is a persisted date (default transaction current date), not a
  moving clock inside a generated expression. Population should provide its
  explicit reproducible snapshot date; future age refreshes must update it.
  The birthday becomes adult at its 18-year anniversary; PostgreSQL's calendar
  arithmetic determines leap-day anniversaries.
- Patient guardian name/relation are either both null or both nonblank. Copied
  minors may lack guardian details until these are collected; preservation does
  not fabricate guardian attribution. A consent attributed to a guardian always
  requires both details on the consent record. Patient-attributed consent must
  omit those details. A SQL deferred check evaluates adulthood at the consent
  `given_at` date in Asia/Hebron, not at the patient's frozen `minor_as_of`.
  Withdrawal cannot precede consent. Consents are historical records: there is
  no uniqueness constraint on one row per patient.
- Patient merges reference another patient and prohibit self-merges. Merge
  candidates are unique, ordered pairs (`patient_a < patient_b`), with score
  between 0 and 1 and a translation-key reason. Execution, merge-cycle detection,
  and merge authorization are future service responsibilities.
- Appointment and visit doctor/clinic pairs reference a valid doctor's home
  clinic. Appointments allow `booked`, `completed`, **`double_booked`**,
  `no_show`, and `cancelled`. Duration is 1–1440 minutes. Update time cannot
  precede creation time. There is deliberately **no unique slot constraint,
  exclusion constraint, or historical-collision cleanup**. Future booking
  conflict logic must preserve source rows and apply its own concurrency policy.
- Alerts reference a valid `(visit_id, patient_id)` pair. SQL additionally
  requires `source_note_excerpt` to equal the **entire exact source diagnosis
  note**, not a paraphrase or inferred medication. Changes to a source visit
  must not invalidate an existing alert. Alert kinds are medication/allergy/
  condition; labels are translation keys.
- Audit references to user/clinic/patient are nullable so system actions can be
  recorded. `action` is nonblank and `detail` must be a JSON object.
- Sync status is pending/applied/conflict/rejected; payload is a JSON object.
  Resolver references a user. This does not implement processing or authorize a
  resolver; service-level permissions remain required.
- Import batches preserve source name/checksum and default review_required.
  Import rows preserve source event ID and original JSON-object payload.
  Suggested and confirmed identities are separate FKs. Confidence is 0–1.
  Review-required rows cannot have confirmed identities, chosen actions, or
  committed appointments. Confirmed review requires explicit create/link/skip;
  link requires confirmed patient and doctor. Rejected rows may only have no
  action or skip, and no appointment. Skip cannot reference an appointment.
  An appointment requires confirmed create/link and both confirmed identities.
  Deferred SQL checks ensure a confirmed doctor belongs to the batch clinic
  and any linked appointment matches the confirmed patient/doctor and clinic.
  There is no FK to the immutable calendar export: `source_event_id` also
  supports future external sources without changing seed privileges.
  Identity-confirmation evidence, batch workflow transitions, and commitment
  orchestration remain service responsibilities. All 24 current calendar source
  rows must initially remain review_required; name matches only suggest.
- Notifications reference patient/clinic and an optional appointment. If set,
  appointment patient and clinic must match. Message fields are translation keys;
  status pending/simulated/cancelled does not send real messages.
- KPI values are finite PostgreSQL numeric values. One partial unique index
  enforces `(date,metric,clinic_id)` for clinic values; another enforces
  `(date,metric)` for network-wide null-clinic values. PostgreSQL numeric values
  (including scores/confidence) are strings in Drizzle/insert validators to
  avoid precision loss.

Foreign keys use NO ACTION, not cascading deletion into operational or seed
tables. A reset must delete the explicit operational allowlist in dependency
order; deferred cyclic references can be cleared in the same transaction.

## SQL versus insert validators

Insert validators cover enums, nonblank strings, translation-key syntax,
email shape, role assignment, duration, numeric range, guardian field pairing,
known patient DOB/as-of/self-merge rules, supplied timestamp ordering, clinic
days/hours/timezone, and import row state/action combinations.

They are **not** database authorization or update/patch schemas. Defaults may
only be fully evaluated by PostgreSQL. They cannot inspect referenced rows or
enforce uniqueness, sequence allocation, clinic/device/doctor consistency,
reciprocal links, age at consent, exact source-note provenance, appointment
identity after import, append-only audit privileges, or cross-request races.
These checks use SQL FKs, indexes, checks, and deferred constraint triggers.
For early transaction failure after populating both halves of cyclic links,
execute `SET CONSTRAINTS ALL IMMEDIATE`; otherwise deferred errors surface on
commit. All trigger functions use invoker security and a pinned `pg_catalog`
search path. No SECURITY DEFINER function is installed.

## Runtime privileges and guarded reset

`amal_app` receives schema USAGE, explicit operational sequence USAGE/SELECT,
and SELECT/INSERT/UPDATE/DELETE on explicitly listed non-audit tables. It receives
**SELECT/INSERT only** on `audit_log`, never UPDATE, DELETE, TRUNCATE, ownership,
or schema CREATE. No blanket public-schema or default-privilege grants occur.
Audit mutation triggers also reject UPDATE/DELETE/TRUNCATE, including attempts
using a user-set configuration variable.

The migration grants membership in dedicated `amal_demo_reset` to the trusted
administrative migration role only and verifies `amal_app` is not a member.
Runtime logins must not receive reset-role membership. The NOLOGIN role receives
only operational schema USAGE and SELECT/DELETE on an explicit operational table
allowlist. It receives no seed privileges, TRUNCATE, INSERT, UPDATE, sequence
reset permission, or ownership. It is not a general population role.

The guarded administrative reset runner must acquire its transaction/advisory
lock, `SET LOCAL ROLE amal_demo_reset` for the allowlisted DELETE phase, then
`RESET ROLE` to its trusted administrative connection before sequence management
and invoking the ordinary population routine. The audit trigger permits DELETE
only while actual `current_user = 'amal_demo_reset'`; even administrators must
use that explicit exception for normal reset deletion. UPDATE and TRUNCATE
remain rejected. There is no app-callable reset function or configuration-GUC
bypass. Demo environment/confirmation guards are the reset runner's additional
responsibility, not an authorization mechanism embedded in these tables.
